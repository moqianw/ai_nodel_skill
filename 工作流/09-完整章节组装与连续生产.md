# 完整章节组装与连续生产

> 协议版本：`CAP-2026-10-09.1`
> 章节组装器版本：`CA-2026-10-09.1`
> 职责：把既有场景编译、独立 B/B2、盲还原和状态账本连接成可恢复的完整章节与跨章连续生产闭环。

## 1. 边界

本协议不增加新的设计阶段，也不增加正文文风规则。它只解决：

- 逻辑事件怎样进入卷级场景地图；
- 多个场景怎样滚动组成自然的物理章；正式连续生产仍以约 2500 字作为默认规划信号，完整正文环境测试则执行不少于 5000 个汉字的覆盖门；
- 场景 DRAFT 怎样经过独立章节组装形成唯一待验收正文；
- 整章通过后怎样原子提交状态，并安全开始下一章；
- 中途失败、边界调整或旧章返修时从哪里恢复。

单场的事实、人物、空间、动作、对白、B/B2 与盲还原仍由 `03`、`04`、`06`、`07`、`08` 负责。本协议不得把章节长度、场景数或转场形式变成固定文学模板。

## 2. 执行单位

| 单位 | 作用 | 是否正式状态 |
|---|---|---|
| 逻辑事件 | 单卷设计中的因果变化单元 | 是，上游设计 |
| 场景地图项 | 可执行的场景功能、进入/离开状态及前后关系 | 是，滚动结构 |
| 物理章计划 | 近期场景组合、章内问题、获得感、章首/章末与篇幅目标 | `SOFT`，可版本化调整 |
| 冻结场景单元 | 单场生成器与 B2 的直接输入 | 是，生成依赖 |
| `SCENE_DRAFT` | 已完成独立 B/B2 和单场桥接核对的章节组件 | 否，不单独提交卷状态 |
| 章节组装包 | 锁定场景顺序、跨场承接、整章边界和组装权限 | 是，组装依赖 |
| `CHAPTER_DRAFT` | 章节组装器输出的唯一整章候选 | 否，验收后才可提交 |
| 章节状态增量 | 整章最终结果相对上一状态的变化 | 是，追加式历史 |

逻辑事件、场景和物理章不是一一对应关系。一个逻辑事件可以跨章，一个物理章也可以包含多个共同完成同一章内变化的场景。

## 3. 完整章节强制链

正式连续正文使用以下链路：

`VALID 单卷设计 → 卷级场景地图 → 3—5章滚动计划 → 当前物理章计划 → 顺序场景编译 → 独立 B/B2 → SCENE_DRAFT + 章内临时状态 → 章节组装包冻结 → 独立章节组装器 → CHAPTER_DRAFT → 整章盲还原/比较/四层审计 → 状态提交事务 → VALID → 刷新滚动窗口`

禁止以下替代：

- 把若干 `SCENE_DRAFT` 直接拼接后当作完整章；
- 仅验收各场景，不验收整章开头、转场、重复、获得感与章末；
- 在上一章仍为 `DRAFT` 时冻结依赖其结果的下一章场景包；
- 先更新状态快照，之后再补增量或验收记录；
- 为达到字数目标向组装器要求重复解释、补环境或拉长动作。

## 4. 从逻辑事件到滚动物理章

### 4.1 卷级场景地图

场景地图从 `VALID` 逻辑事件展开，但只保留跨场景有价值的信息：

- `scene_id` 与来源逻辑事件；
- 场景功能及必须发生的变化；
- 进入状态与离开状态；
- 信息释放、隐藏和读者问题；
- 与前后场景的因果、时间、空间或关系连接；
- 初步章界建议及可与相邻场景合章/拆章的条件。

地图不保存最终对白、微动作、一次性站位或固定字数。

### 4.2 3—5章滚动计划

滚动计划对近期物理章记录：

- `chapter_id`、计划版本和状态；
- 承接的 `scene_id` 顺序；
- 章首如何接住上一 `VALID/PUBLISHED` 章；
- 本章核心问题与主要叙事发动机；
- 读者完成本章后实际获得什么；
- 章末落点及它怎样推动下一章；
- 目标字数、计划区间和各场景篇幅权重；
- 允许调整章界的条件。

章界状态分为：

- `PROPOSED`：滚动计划中的建议，可直接改版；
- `FROZEN_FOR_RUN`：本章已有冻结场景单元，调整会触发依赖检查；
- `VALID`：整章与状态已提交，改变章界属于正式章节返修。

物理章边界在滚动计划中先行确定，不等全卷正文完成后再机械切分；实际正文暴露节奏问题时允许改版。

### 4.2.1 章节读者价值

章计划除事件/字数外，标清本章读者真正可获得什么、值得展开的场景与可以概述的过程，保留人物特有的临场反应；不要求每章强冲突或固定悬念。若篇幅主要被琐碎正确操作占据，先改场景权重/章界而不是填充。

### 4.3 篇幅与密度

- 正式连续生产默认规划目标为约 2500 字，建议工作区间为 2200—3000 字；这是调度信号，不是质量分数或硬切线。
- 完整正文环境测试建议目标为 5500—7500 个汉字，最终 `CHAPTER_DRAFT` 硬下限为 5000 个汉字。该下限验证长章持续组织能力，不改变未来正式章节的默认篇幅。
- 测试章自然内容不足时必须扩大连续正式事件范围或重编章界；禁止为越过 5000 字补重复检查、静态环境、解释性心理、同义总结或无动机收尾。
- 低于或高于工作区间时，先检查章界、事件密度和场景必要性，不自动判失败。
- 过短且没有完整获得感时，优先调整章界或补回本应正面发生的场景内容；不得添加无功能动作、环境、心理解释或总结。
- 过长且存在自然阶段边界时，优先拆章并重编承接；不得按字数在连续动作中间硬切。
- 正当的短章或长章可保留，但须在章计划和验收记录中说明其叙事理由。

## 5. 多场景顺序生产

### 5.1 当前章基础状态

第一场只从上一 `VALID/PUBLISHED` 章版本、当前正式快照和当前章计划编译。章内后续场景另使用一个不进入正式账本的 `chapter_working_state`，至少保存：

- 已完成场景及其 DRAFT 哈希；
- 当前时间、位置、人物身体、物品、认知和关系临时投影；
- 读者已在本章获得的信息；
- 尚未完成的本章义务；
- 下一场景需要的读者可见前文。

`chapter_working_state` 只服务当前章。它不能越过整章验收写入正式状态快照。

### 5.2 场景串行与失效传播

每个场景仍独立执行 `编译 → FROZEN → B → B2`。B2 输出后进行一次独立的场景桥接核对，确认离开状态、读者可见信息和下一场景入口可以从正文恢复，才登记为 `SCENE_READY`。

场景必须按依赖顺序生成。前一场景正文或桥接状态发生变化时：

- 直接依赖它的后续场景包立即 `STALE`；
- 尚未生成的场景重新编译；
- 已生成的后续场景保留为历史产物，但不得继续组装；
- 不依赖该变化的并行场景无需机械作废。

场景核对只是组装前门槛，不代替整章盲验。

## 6. 章节组装包

全部计划场景达到 `SCENE_READY` 后，控制器冻结 `CHAPTER_ASSEMBLY_PACKAGE`。至少记录：

- `chapter_id`、章计划版本、上一 `VALID/PUBLISHED` 章版本与状态版本；
- 有序 `scene_id / package_id / SCENE_DRAFT` 哈希；
- 本章必须完成、不得提前完成及最终离开状态；
- 章首承接、场景间时间/空间/行动权/视角转移和章末落点；
- 跨场景重复、重入说明、无效退场/再入场的压缩范围；
- 目标字数、工作区间和允许偏离理由；
- 最近3—5章重复窗口；
- 章节组装器版本、运行时协议版本及依赖向量；
- 组装器可以调整和禁止调整的边界。

任一场景 DRAFT、章计划、上一章、正式状态、声音/PDM、近期重复窗口或组装协议变化，章节组装包自动 `STALE`。

## 7. 独立章节组装器

章节组装器必须使用新的独立上下文，只接收：

1. 状态有效的 `CHAPTER_ASSEMBLY_PACKAGE`；
2. 有序的最终 `SCENE_DRAFT`；
3. 包内确定的上一章读者可见末尾；
4. 包内章节级声音、重复和篇幅提示。

不得接收 RAW_DRAFT、完整仓库、Oracle、验收意见、历史失败正文或生成推理。

章节组装器可以：

- 删除重复的场景重入、退场和同义回顾；
- 修复章首承接、场景间过渡、视角重定位和章末落点；
- 在不改变真实因果顺序时调整场景交界处的信息位置；
- 重新分配过渡段、日常余波和必要心理的篇幅；
- 合并强连续场景边界，或保留明确时空跳转。

章节组装器不得：

- 改变任一冻结场景的关键事实、认知上限、必要证据、主要因果或离开状态；
- 为凑字数新增事件、设定、检查步骤、环境陈列或解释性心理；
- 把未通过的场景内容隐藏在更顺的语言里；
- 读取下一章后台答案后反向制造伏笔。

若整章成立必须改变冻结场景边界，返回 `ASSEMBLY_BLOCKED`，由控制器改版章计划或场景包。成功时只输出 `chapter_id + CHAPTER_DRAFT`。

章节组装器还须核对编辑损益：不得为了删除过场而抹掉人物间有效的玩笑、迟到反应、关系上的不整齐回应和余波；同一章角色应仍可辨。

## 8. 整章统一验收

整章验收使用另一个新上下文，顺序不可反转：

1. **盲还原**：只读上一章必要可见末尾和完整 `CHAPTER_DRAFT`，冻结本章时间/空间、场景转换、人物认知、关系变化、重要物体、读者获得、章末状态及无法确定项。
2. **比较验收**：再读章节组装包、各冻结场景单元和验收协议，比较场景锁定边界与整章实际表达。
3. **章节审计**：检查章首承接、场景顺序、跨场重复、详略、适用的篇幅/密度门、章节获得感、自然章末、下一章推动及最近3—5章同构。完整正文环境测试另核验正文不少于 5000 个汉字且没有注水。

以下任一项不能由单场通过抵消：

- 场景之间缺少可恢复的时间、空间、行动权或视角承接；
- 每个场景各自成立，但整章没有核心问题、变化或读者获得；
- 为达到篇幅重复解释、重复检查或添加无功能描写；
- 章首重复上一章已完成内容，或章末只总结本章意义；
- 组装过程改变了场景锁定事实或遗漏必要结果；
- 下一章所需状态只存在于后台包，没有在正文中建立。

整章还须经独立读者盲读，只有本章正文与上一章可见结尾可作输入；需具体指出本章的实际阅读价值、场景权重和组装损失。`READER_FAIL` 或 `REVIEW_INSUFFICIENT` 都不可因事实 PASS 而进入 PREPARED，详见 [`10-读者体验与假阳性防护.md`](10-读者体验与假阳性防护.md)。

只有整章验收通过，`CHAPTER_DRAFT` 才能进入状态提交准备。

## 9. 状态提交事务

整章状态提交采用 `PREPARED → COMMITTED` 两阶段：

### 9.1 PREPARED

控制器根据最终 `CHAPTER_DRAFT` 和冻结验收结果准备：

- 不可覆盖的章节状态增量；
- 更新后的最新状态快照；
- 章节验收记录；
- 物理章映射、实际字数和滚动计划新版本；
- 运行台账的最终任务/哈希/隔离凭据。

任一文件无法形成连续版本时停止，正文保持 `DRAFT`，正式快照不前移。

### 9.2 COMMITTED

上述文件必须在同一次可追溯提交中完成。提交成功后才：

- 将正文标为 `VALID`；
- 将 `chapter_working_state` 的最终结果投影为正式状态；
- 使依赖旧快照的未启动包失效；
- 滚动补足未来3—5章计划；
- 允许下一物理章冻结首个场景包。

部分提交、仅改快照、仅写增量或只有正文文件均不算 `VALID`。

## 10. 调度台账与恢复

每次章节运行维护一个控制器台账，至少包含：

- `run_id / chapter_id / attempt`；
- 章计划、场景地图、状态和协议版本；
- 每个场景的编译、B、B2、桥接核对上下文标识及产物哈希；
- 章节组装器和整章验收上下文标识及产物哈希；
- 当前状态、最后安全点、阻塞原因和下一动作；
- 隔离资格、重试次数及是否读取过禁入材料。

章节运行状态使用：

`PLANNED → SCENES_RUNNING → SCENES_READY → ASSEMBLY_FROZEN → CHAPTER_DRAFT → AUDITING → PREPARED → VALID`

异常状态：`BLOCKED / STALE / SUPERSEDED / INVALID`。

恢复规则：

- 工具或传输失败：从最后一个已核对哈希的安全点恢复，不重跑已完成独立任务；
- `COMPILE_BLOCKED`：补编负责层或调整计划，生成新包；
- `EDIT_BLOCKED`：不得让 B2 自行补事实，返回场景编译；
- `ASSEMBLY_BLOCKED`：先判断章界错误还是场景锁定冲突，再改版对应层；
- 内容验收失败：正式正文可按现有受控返修边界处理；需要改变状态时必须新包；
- 隔离污染：该独立任务产物记 `INVALID`，使用新上下文重做，不把污染意见传给生成侧；
- 连续两次同类失败：停止盲目重抽，审计负责层和调度输入。

## 11. 跨章连续生产

- 下一章的冻结输入只能来自上一 `VALID/PUBLISHED` 章、已提交快照和新滚动计划；不能依赖仅存在于 DRAFT 的结果。
- 章首先判断是否延续同一现场。强连续时承接上一章未完成动作或压力；发生时间、空间、任务或视角重置时重新建立人物与现场，不用悬空代词或摘要硬接。
- 章末落点须写入下一章计划的进入条件，但不提前编译下一章具体台词和微动作。
- 每章提交后更新近期重复窗口；每3—5章执行 checkpoint、增量重放和语言/结构稳定审计。
- 旧章返修从其增量和运行台账定位真实依赖。最早受影响章之后的场景包、组装包和正文按依赖标记 `STALE/待重审`，不机械推倒无关章节。

## 12. 验证顺序

本协议补全不宣布正文能力已经通过，也不授权批量正式正文生产。项目按以下顺序验证：

1. 旧 PDM05、自由校准、VQ-A/VQ-B、Q01 AI PASS 与 T01—T08 全部仅作历史结果，不再运行；
2. 从第一卷 L01 起，以连续正式事件编译一章不少于 5000 个汉字的完整正文环境测试，执行独立 B/B2、独立章节组装和整章读者/事实双门，并交作者判断；
3. 作者认可后再决定是否按正式状态事务重编首章，并实测第二章的跨章状态和自动恢复；测试稿本身不直接转正；
4. 连续两章通过后扩大到连续5—10章，检查篇幅、结构重复、人物漂移、节奏和状态账本；
5. 未通过时只修改实际负责层，不用追加文风禁令或退回短篇测试代替调度修复。
