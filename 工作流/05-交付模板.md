> **跨作品交付模板：** 在执行下面的任何提示词前，先读取[项目路由](../项目路由.md)；以用户指定项目或路由中的 `PROJECT_ROOT` 替换所有作品目录。通用工作流在根目录 `工作流/`，小说内容、状态与运行记录必须留在 `PROJECT_ROOT/`，不复制工作流，也不创建 `小说项目/`。

# 工作流交付模板

## A. GitHub 项目模式（默认）

当 Web Chat 能通过 `@GitHub` 读取当前仓库时，作者最短只需输入：

```markdown
@GitHub 读取当前仓库 main 分支，按项目路由选择我的小说项目，依据公共工作流启动当前可开始的设计阶段。每轮分为“本轮作者确认 / 模型解释与必要推导 / 下一轮问题”；不要把其他书设定带入本项目。
```

开始其他阶段时，只替换阶段名称或卷名。

收到这类指令后，Web Chat 应自动执行：

1. 读取当前仓库 `main` 最新版的根目录 `AGENTS.md` 以及 `项目路由.md`，解析本轮用户指定或默认的 `PROJECT_ROOT`；
2. 读取 `PROJECT_ROOT/项目状态.md`；
3. 读取：
   - `工作流/00-工作流总则.md`；
   - `工作流/01-三层问答与设计记录.md`；
   - `工作流/05-交付模板.md`；
4. 根据当前阶段读取 `PROJECT_ROOT/正式资料/00-总索引.md`、对应 `VALID` 上游资料及其中登记的覆盖缺口；
5. 若当前项目属于重构，读取 `参考库/00-使用说明.md`，并按项目状态或作者指定范围读取必要的 `REFERENCE` 资料；不要默认读取全部旧正文；
6. 正式提问前，先把旧资料分为“明显仍需重新设计、与新版冲突、高概率可以直接继承、低影响可暂时继承”，向作者提供简洁分类和一次批量授权选项；
7. 不要求作者重复粘贴仓库里已有的项目状态、有效上游或旧资料；
8. 建立当前阶段覆盖账本，使用连续三层问答逐域推进；每次收到回答，下一条按“本轮作者确认 / 模型解释与必要推导 / 下一轮问题”组织。第一段只回显作者采用项、改写项、否定、例外和覆盖关系，并把被选选项的完整兼容语义展开，不能只回显题号字母或压缩结论；模型新增解释、必要推导和可选建议放在第二段并区分身份；
9. 在所有必要领域均已覆盖、继承、可靠推导、明确后置或说明不适用前，不宣布阶段结束；
10. 阶段结束时不生成结构化总结、决策总表、有效记录或大纲，只提示作者将完整对话保存到 `PROJECT_ROOT/设计记录/` 并交给项目 Agent。有效记录由项目 Agent 生成。

若 GitHub 连接无法读取某个必要文件，应指出具体路径，只请求补充缺失材料，不把整个项目重新交给作者粘贴。

## B. 手工粘贴模式

没有 GitHub 或文件访问能力时，使用以下模板：

```markdown
你现在协助我完成小说创作的【阶段一：小说基础模型 / 阶段二：全书架构 / 阶段三：第X卷设计】。

请读取我提供的工作流与上游材料，使用“三层问答 + 阶段覆盖表”持续提问：
1. 先确认方向与结构；
2. 再逐域补齐必要内容、重要分叉和关键缺口；
3. 最后审计冲突、逻辑后果与覆盖完整性。

不要重复已经确认的内容，也不要以“不机械填表”为理由漏掉整个领域。能由现有确认唯一推出的事项标为 DERIVED；属于后续阶段的事项要明确写出后置位置；你提出但我未接受的方案不能写成作者决定。

如果我提供旧资料，先提取继承候选，分为：明显仍需重新设计、与新版冲突、高概率可以直接继承、低影响可暂时继承。先请求一次批量授权，再询问真正需要决定的内容。

每次收到我的回答，下一条使用三个轻量标题：
1. 本轮作者确认：完整回显我采用、组合、改写、否定的内容以及覆盖关系；若我选择字母项，要把该项完整兼容语义展开，不能只写题号字母或一句摘要；不要混入你的新增方案。
2. 模型解释与必要推导：必要后果写出依据；高置信解释和可选建议分别说明，不能自动算我的决定。
3. 下一轮问题：集中写问题、候选项、推荐与答题方式。

阶段结束时不要总结，不要生成设计报告，只提示我保存 Web Chat 的连续输出并交给项目 Agent。

本轮范围：〔填写〕
本轮不处理：〔填写〕
当前项目状态：〔粘贴相关部分〕
有效上游材料：〔粘贴或链接〕
继承候选来源：〔可空；粘贴或链接作者指定旧资料〕
```

## C. 完整问答记录保存格式

常规交接不再要求 Web Chat 生成总结。把整段对话保存为一个 Markdown 文件即可：

```markdown
# 〔阶段/卷名〕原始记录

- 日期：YYYY-MM-DD
- 适用阶段：小说基础模型 / 全书架构 / 第X卷设计
- 记录状态：待编译
- 直接上游：〔可选链接〕

## Web Chat 连续输出

〔按时间顺序粘贴 Web Chat 的全部输出，不压缩、不重写。若导出同时包含作者发言，可以一并保留。〕
```

保存要求：

- 当前默认只要求保存 Web Chat 输出，不要求作者另外补写自己的回答；若导出包含双方发言则原样保留；
- 每轮“本轮作者确认”必须完整包含作者选择、组合、自定义文本、否定、例外和覆盖；
- 不删除被后文覆盖的旧决定，项目 Agent 需要它们判断修改链；
- 不要求为对话手工编号，也不要求作者手工添加 `CONFIRMED / DIRECT / HARD` 等标签；
- 旧式记录若在末尾已有 Chat 总结可以原样保留，但总结只作导航，不作为编译依据。

## D. 交给项目 Agent 的编译请求

最短请求：

```markdown
已完成〔阶段名称〕，Web Chat 原始记录已放入〔文件路径〕。请按现行工作流判断编译模式，完成三遍语义审计，分别生成证据包与当前有效记录并编译正式资料；不要修改原始记录，不要把模型建议当成作者决定，也不要用脚本筛选结果代替语义覆盖检查。
```

项目 Agent 自动执行：

- 从头到尾读取原始记录，按实际结构分离作者决定回显、模型解释/推导和下一轮问题，并判断使用旧记录兼容模式还是新版原生模式；
- 直接从原始记录生成独立证据包，保存逐轮处理区、来源定位与覆盖证据；旧格式回显缩略时恢复被选方案全文，新版三段式确认已经完整时不重复生成选项层；
- 生成按主题组织的当前语义层：可合并、改写与重排，但不得损失条件、例外、因果、心理、关系、信息差、具体实现、叙事目的和否定项；
- 为有效记录的每个信息单元登记正式落点、后置、仅建议、被覆盖或不适用，并从正式资料反向审计遗漏；
- 应用全部适用的作者确认，按后文覆盖前文，并防止否定内容回流；
- 分别处理决策状态、来源类型和约束强度，不把 `DERIVED` 与 `HARD / SOFT` 混为同一维度；
- 只编译当前授权覆盖的 `INHERITED` 内容，遇到新版冲突时使继承项失效；
- 将继承内容真正写入当前正式资料，不直接把参考库当作正式事实引用；
- 对未被问到的内容不自行虚构：非阻塞项进入待定/后置清单，阻塞性 `HARD` 缺口才提出最小补问；但所有当前有效、会影响下游执行的信息，无论 `HARD` 或 `SOFT`，都必须获得正式落点；
- 为重要跨文件依赖补直接来源链接或章节级依赖声明，不给普通低风险叙述逐条加链；
- 同步更新项目状态、依赖状态和修改记录；
- 只有身份、语义覆盖和一致性检查通过后才标记 `VALID`；最终汇报修改范围、状态变化、实际遗漏、自动修复、证据不足问题和下一步。
