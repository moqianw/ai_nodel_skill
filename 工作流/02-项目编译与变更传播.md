# 项目编译与变更传播

## 1. 编译的定义

“编译”是完整读取阶段原始记录，按时序恢复作者决定与证据边界，生成独立证据包和当前语义有效记录，再转换为正式文件，同时维护事实身份、来源链接、覆盖缺口、状态、依赖和修改历史。它不是再次创作一轮，也不是用脚本筛掉选项后把剩余文本原样复制进大纲。

## 2. 编译优先级

出现冲突时按以下顺序判断：

1. 用户当前明确指令；
2. 当前对话中作者明确确认；
3. 最新且适用的有效记录中的作者决定、当前继承授权与可靠推导；发生身份、覆盖或来源争议时先读对应证据包，仍不足再回查原始记录；
4. 当前 `VALID` 正式文件；
5. 由当前有效事实可靠推出的内容；
6. 未经当前授权的参考库、历史记录、旧大纲与旧正文；
7. Agent 推断。

同一级别内，后文通常覆盖前文；但作者确认永远优先于模型建议。记录末尾由 Chat 生成的压缩总结不构成新的作者决定，与前文冲突时必须回到完整时序判断。

## 3. 标准编译流程

1. **确认原始结构与编译模式**：判断使用旧记录兼容模式还是新版原生模式；识别记录是否只含 Web Chat 输出、每条输出中哪里处理上一轮回答、哪里提出下一轮问题；没有作者发言时不得假装已独立核验其原话。
2. **第一遍按时序通读**：恢复“模型提出候选—下一条输出回显作者决定—模型解释/推导—后文修改—最终覆盖”。不得先读末尾总结后反向套用全文。
3. **按模式恢复被选方案**：作者决定回显、模型必要推导、高置信解释、未确认建议和下一轮候选分别处理。旧记录回显若只有字母、组合项或推荐项，回到上一轮提取方案全文，与回显和自定义修改合并；新版原生记录的确认区语义完整时不重复恢复，只有争议时回查。继续下一轮不构成对模型扩展内容的默认接受。
4. **拆解旧式阶段整理**：记录末尾的总结或设计记录逐项核对，不整体采信也不整体丢弃；每项分别回链为作者决定复述、可靠 `DERIVED`、未确认建议、被覆盖或证据不足。
5. **提取三维身份**：分别判断 `CONFIRMED / TENTATIVE / PENDING / REJECTED`、`DIRECT / DERIVED / INHERITED`、`HARD / SOFT`；建立防回流与失效条件。
6. **分别生成证据包与当前有效记录**：证据包保存直接来自原始记录的处理区逐字保全、来源定位、覆盖证据、旧格式选项恢复和迁移比对；当前有效记录只按主题保存全部当前有效独立语义、覆盖拒绝、后置和正式映射。条件、例外、限制、反例、因果、心理、关系、信息差、具体实现、叙事目的、读者体验和否定项不得因瘦身丢失；原始记录不改写。
7. **第二遍阶段覆盖审计**：按覆盖表逐域检查，区分已覆盖、已继承、可推导、明确后置、不适用和真正缺失；记录未映射信息，不用自动化长度或关键词命中代替语义判断。
8. **建立有效记录到正式资料的映射**：每个信息单元明确归为已编译、明确后置、仅建议、被覆盖或不适用；复杂事件和关键规则链接到有效记录的可定位章节。证据包中出现但当前有效记录未单列的信息也必须获得身份与处理结论；“有效记录没有收录”本身不能视为无效。
9. **按阶段完整度编译**：阶段一保留规则链、条件例外、人物弹性、家庭资源、关系知情、长期秘密与必要前史；阶段二保留全书因果、各卷变化/依赖、人物与特殊机制/关系线、具体事件、伏笔信息顺序、时间资源和不可逆结果；阶段三按可执行事件标准落地。
10. **解决冲突与缺口**：以后文有效决定覆盖前文；作者决定覆盖模型建议。非阻塞项明确后置；影响核心方向的证据不足只提出最小问题，不静默补写。
11. **第三遍正式资料反向审计**：查条件/例外/来源遗漏、建议冒充决定、被覆盖旧规则回流、目标与实现混淆，以及人物心理、关系、知情差、计数、顺序和时间被压缩；逐项判断删除后是否会改变下游设计、人物表现、事件实现、现实条件或正文体验。
12. **传播变更**：检查下游，只更新实际受影响的文件；不能立即重编的原有效内容标为 `DIRTY`，尚未建立者保持 `UNBUILT / BLOCKED`。
13. **状态验收**：只有信息身份、语义覆盖、执行相关信息落点、内部一致性、来源链接和状态都通过，且不存在未处理的当前有效执行相关信息，才将阶段标为 `VALID`；同步更新项目状态与修改记录。

## 4. 状态管理

- `VALID`：本文件已与当前上游一致。
- `DIRTY`：本文件原本已有当前版本有效内容，但因上游变化需要重新审计或编译。
- `UNBUILT`：当前版本尚未建立；不表示存在旧内容需要重编。
- `BLOCKED`：当前版本尚未能开始，因为必要上游尚未达到可用状态。
- `REFERENCE`：仅作历史、样本或素材，不能反向约束当前设计。
- `DEPRECATED`：已被其他规则或文件替代，只保留跳转或追溯价值。

常见状态转换：

- 新阶段可以开始但尚无资料：`UNBUILT`；
- 新阶段因上游未完成而不能开始：`BLOCKED`；
- 上游完成后：`BLOCKED → UNBUILT`；
- 完成设计并编译：`UNBUILT / DIRTY → VALID`；
- 原有 `VALID` 内容受上游变化影响：`VALID → DIRTY`。

状态记录集中放在 `PROJECT_ROOT/项目状态.md`（由[项目路由](../项目路由.md)解析）。正文文件中只在容易误用时增加简短醒目标记，不要求每页复制状态表。

每次正式编译在 `项目状态.md` 的变更记录中追加一条简表：日期、原始记录、证据包与当前有效记录、修改范围、最高影响等级、哪些文件改变状态。项目状态和审计可以链接证据包或原始记录用于历史追溯；正式小说资料链接有效记录的主题章节。

## 5. 三个事实维度

三个维度必须分开记录：

### A. 决策状态

`CONFIRMED / TENTATIVE / PENDING / REJECTED` 表示作者是否作出决定。

### B. 来源类型

| 类型 | 含义 | 编译要求 |
|---|---|---|
| `DIRECT` | 作者在当前有效问答中直接表达确认、倾向、否定或明确授权；只有 Chat 输出时，需有清楚归因于作者的逐轮确认回显 | 链接有效记录；争议时先查证据包，仍不足再查原始记录 |
| `DERIVED` | 由其他当前有效事实可靠推出 | 记录依据与失效条件 |
| `INHERITED` | 从指定参考资料提取，并获得当前明确或批量授权 | 记录授权范围及参考来源；不得直接引用参考库充当当前事实 |

### C. 约束强度

| 类型 | 说明 | 修改要求 |
|---|---|---|
| `HARD` | 作品核心承诺、底层规则、结局约束、关键人物本质或主因果 | 必须有作者确认，并审计广泛影响 |
| `SOFT` | 当前采用的设计和实现，可在保留目标时调整 | 说明替代方案及局部影响 |

同一事实可以是 `CONFIRMED + DERIVED + HARD`，也可以是 `TENTATIVE + DIRECT + SOFT`。`L1—L4` 只表示修改影响范围，是第四个独立判断。

来源为 `DERIVED` 的事实会在推导依据失效时自动失效，但不因此天然等于低约束。对仍然有效的事实，默认优先调整 `SOFT`，再调整 `HARD`。用户当前明确要求可以修改任何强度。

## 6. 继承候选的编译

参考库始终是 `REFERENCE`。批量继承改变的是“本轮对某些候选的授权”，不是参考库状态。

1. 核对候选是否来自作者指定、或 `项目状态.md` 为本轮登记的参考范围。
2. 核对完整问答是否包含四类候选结论：明显仍需重新设计、与新版冲突、高概率可以直接继承、低影响可暂时继承。
3. 只编译批量授权覆盖的范围；例外项、冲突项和未获授权项不得进入正式资料。
4. 对 `HARD` 候选，要求当前明确授权或由当前有效资料提供明确兼容依据；一般性的“其余都继承”默认只覆盖清楚列明的稳定低风险范围。
5. 批量继承的稳定内容可记为 `CONFIRMED + INHERITED`；暂时沿用的低影响内容可记为 `TENTATIVE + INHERITED`。二者仍需独立判断 `HARD / SOFT`。
6. 将获准内容改写并编译进当前正式资料。可以在文件或章节级统一声明继承来源，不要求每条低风险事实单独加链接。
7. 新版决定与继承内容冲突时，新版决定优先，继承项自动失效并从正式资料删除或改写。

## 7. 设计目标与当前实现

当作者希望保留某种体验，却允许改变实现时，必须拆写：

- **设计目标**：想让读者感受到什么、人物关系承担什么功能、某段结构解决什么问题；
- **当前实现**：目前用哪个事件、能力、人物安排或叙事手法实现；
- **替换条件**：什么情况下允许换实现；
- **不可损失项**：替换后仍必须保留的效果。

反向修改时优先保护设计目标，不把旧实现误当成不可变规则。

## 8. 影响等级

| 等级 | 影响范围 | 默认处理 |
|---|---|---|
| `L1` | 单一表述、命名、局部动作或不改变因果的细节 | 直接修改并做邻近检查 |
| `L2` | 一个事件链、一个人物阶段、一个能力用法或单卷局部 | 修改负责文件并检查同卷依赖 |
| `L3` | 多卷结构、核心关系、主线因果、重要世界规则 | 已有有效下游标记为 `DIRTY`，未建立下游按依赖保持 `UNBUILT / BLOCKED` |
| `L4` | 作品定位、基础模型、结局承诺或世界底层 | 从最上游重新审计，旧架构降为 `REFERENCE` |

影响等级按实际后果判断，不按修改字数判断。

## 9. 正向传播

上游改变后：

1. 找出直接依赖它的文件；
2. 判断每个依赖是仍成立、需局部修改还是整体失效；
3. 能立即修复的同步修改；
4. 不能安全修复且原本为 `VALID` 的标为 `DIRTY`，写清触发原因；尚未建立的下游保持 `UNBUILT` 或 `BLOCKED`；
5. 不受影响的内容继续保持 `VALID`，禁止机械推倒重来。

## 10. 反向修改

正常生成时，下游必须遵守当前有效上游，Agent不得为了让剧情更方便而静默修改世界规则、核心人物、核心能力或结局约束。只有用户明确希望保留某个下游结果、认为上游妨碍更优方案，或明确要求修改上游时，才进入反向修改。

下游设计暴露上游问题时：

1. 记录下游遇到的具体矛盾；
2. 找出原上游条目的设计目标；
3. 提出最小上位修改；
4. 判断是修实现还是改目标；
5. 评估 `L1—L4`；
6. 同步修改上游负责文件和受影响下游；
7. 在修改记录中写明“由哪个下游问题触发”。

不得仅在细纲或正文中偷偷绕开上游规则。

## 11. 来源链接规则

- 必须建立直接来源链接的内容主要包括：世界规则、能力规则、核心人物事实、关键人物状态变化、主因果、跨卷依赖、伏笔与回收、会触发变更传播的事实，以及重要修改来源。
- 问答导致以上重要事实改变时，在相应条目、章节依赖声明或修改记录中链接对应有效记录。
- 同一文件大量使用另一个负责文件中的事实时，可以在文件开头或相关章节建立一次依赖声明，不必逐句重复链接。
- 普通重复叙述、局部表现、同页已定义内容、无争议低风险信息、常识和纯格式文字不要求逐条链接。
- 有效记录是正式文件可引用的直接设计来源。复杂规则、关键人物、重要事件和心理/关系变化应链接到有效记录的对应标题锚点；普通信息可使用文件级依赖声明，不必逐句加链。
- 有效记录集中链接证据包；证据包再链接原始记录。正式资料不得绕过当前有效记录直接把证据包或原始记录当成当前事实来源。
- 链接应足以支持追溯和变更传播，但不能把正式资料写成数据库式文档。链接负责证明重要来源，状态负责说明文件能否使用。

## 12. 正式资料完整度标准

### 阶段一

正式基础模型不能只列高层结论。应完整承载世界与能力规则的形成链、限制、例外和边界案例；核心人物的性格弹性、家庭/资源、关系与知情；长期保密、终局约束及会影响当前故事的重要前史。

### 阶段二

正式全书架构应完整承载主因果、每卷关键变化和卷间依赖、人物/关系及适用的特殊机制长期线、已确认具体事件、伏笔与回收、信息释放顺序、时间/经济/空间资源、各卷代价与不可逆结果。设计目标和当前实现必须并存，不能只剩卷级口号。

### 阶段三

每个逻辑事件至少应能恢复：进入状态、功能、触发、参与人物、人物目标与动机、具体过程、当时知情、心理与关系位置、信息差、冲突、关键选择与解决、已确认细节/动作/场景要求、结果、关系变化和下游接口。可借助文件级依赖避免机械重复，但不能把已确认具体过程压成抽象一句，也不能补写原记录未确认的对白和微动作。

### 执行相关信息

`HARD / SOFT` 只表示修改成本，不决定是否进入正式资料。若删除一条当前有效信息会改变世界规则、人物行为或心理、关系状态、知情与信息差、事件顺序或实现、日常节奏、现实条件、伏笔或正文体验，它就是执行相关信息，必须有正式落点或明确归为后置、仅建议、被覆盖、不适用。

### 阅读成本

固定按需读取顺序为：当前任务正式资料及必要上游正式资料 → 对应有效记录主题 → 对应证据包 → 原始记录。满足任务需要后立即停止下钻。正文 Agent 若经常必须读取有效记录或证据包才能恢复已确认执行信息，应补编正式资料，而不是把下钻变成常规流程。完整不等于把同一长文本复制到每一层。

## 13. 重新编译既有项目

项目中途接入本工作流时：

1. 不先改内容，先建立状态表；
2. 识别最上游的可靠材料和最上游的冲突；
3. 将文件按 `VALID / DIRTY / UNBUILT / BLOCKED / REFERENCE / DEPRECATED` 分类；
4. 选择一个阶段作为重编入口，并从指定参考资料生成继承候选；
5. 对稳定低风险内容进行一次批量授权，只对必须重做、发生冲突或缺失的核心决定开展问答；
6. 将获准继承内容与新决定一起编译进正式资料；
7. 编译完成后再解除下游阻塞并恢复创作。

旧版本可以保留用于回收好点子，但不应凭文件数量或完成度获得更高权威。

## 14. 编译验收清单

- 原始记录中所有适用的作者决定回显是否已提取，后文覆盖关系是否正确；
- 是否生成独立证据包与当前语义有效记录，并保持原始记录未改动；
- 有效记录是否保留所有当前有效独立信息、条件、例外、因果、心理、关系、信息差、具体实现、叙事目的和否定项；
- 编译模式是否判断正确；旧记录被选择选项的完整正文是否已恢复进证据包，新版原生记录是否避免了无意义的重复选项层；
- 模型解释、必要推导与未确认建议是否被正确区分；作者继续下一轮是否被误当作接受模型扩展；
- 有效记录的每个信息单元是否已归为正式落点、明确后置、仅建议、被覆盖或不适用；是否存在未映射的当前有效信息；
- 是否存在仍有效但只留在证据包、未进入有效记录和正式资料的独立执行相关信息；
- 是否存在因标为 `SOFT` 而被省略、但会改变下游设计或正文表现的信息；
- 正式资料是否出现只有结论没有条件/过程，或只写设计目标却丢失当前实现；
- 是否仍保留不必要的正式“全量有效信息”逐字副本；清理前是否确认重要信息已有可靠落点；
- 正式资料是否直接链接证据包或原始记录；如有，应改为对应有效记录主题；复杂规则、关键人物和重要事件是否具有章节级定位；
- `REJECTED` 内容是否仍从旧文件回流；
- 模型建议是否被误写成作者确认；
- 是否逐域完成第二遍覆盖审计，并把真正缺失与明确后置区分开；
- 是否误把 Chat 的阶段总结当作作者决定，或遗漏总结没有收进去的细节；
- 每个重要结论是否分别标明决策状态、来源类型和约束强度；
- `DERIVED` 是否能够追溯到有效依据，并写明失效条件；
- `INHERITED` 是否处于批量授权范围内，且已经编译进正式资料而非直接引用参考库；
- 直接受影响的文件是否已修改或标脏；
- 尚未建立或依赖未满足的文件是否误标为 `DIRTY`；
- 无关的有效内容是否被误删；
- 需要支持追溯与变更传播的重要跨文件事实是否有正确链接或依赖声明；
- 项目状态和修改记录是否同步；
- 是否越过当前阶段擅自扩写了后续内容。

脚本可以辅助生成分段候选、问题编号、证据包和初步清单，但不能证明语义无损。`VALID` 必须来自人工语义审计，并确认没有未处理的当前有效执行相关信息，而不是“未选项为零”、关键词覆盖率或保留字数比例。


## 15. 正文、文风反馈与发布状态的变更传播

正文层也参与变更管理，但不把每个临场小动作升级为上游设定。

### 正文新增信息分级

每章通过验收后，把新出现的信息分成三类：

1. **一次性表现细节**：只服务当前句段，不需要跨章保持。正文保留即可。
2. **连续性细化**：后续场景需要保持一致，例如物品当前位置、刚发生的伤势、临时约定、关系微变化、人物刚形成的误解。先追加本章状态增量，再投影到最新正文状态快照。
3. **上位事实**：会改变人物长期行为、世界规则、跨卷因果、稳定背景或既有正式资料。不得仅靠正文现场决定，必须走本文件的反向修改与传播流程。

### 作者正文反馈

作者对正文的反馈先判断负责层，不默认堆入文风文件：

- 单场前提、临时站位、一次动作或局部句段问题，只修改当前正文/场景执行包，必要时登记回归故障摘要；
- 稳定的人物信息处理、表达、追问、风险或结论倾向，编译进人物执行画像；
- 机械、制度、身体、能力触发或现实条件错误，编译进对应机制/现实负责文件；
- 只有跨人物、跨场景成立的叙事距离、句段、对白嵌入、旁白和 AI 味问题，才编译进项目文风基线；
- 规则已经存在却在换场景或冷启动中没有被使用，修改场景执行编译、正文生成许可、反向状态还原或回归测试；
- 若反馈实际改变事件因果、人物本质或作品承诺，按普通上游变更处理。

同类错误在两个及以上不同性质场景复发时，优先审计执行协议，而不是继续增加局部文风禁令。

### 正文状态

- `SCENE_DRAFT`：由依赖有效的冻结场景单元经独立 B/B2 形成，只是当前章组件，不作为跨章事实。
- `DRAFT`：由依赖有效的章节组装包形成 `CHAPTER_DRAFT`，但尚未通过整章盲还原比较和验收，不作为可靠下游事实。
- `VALID`：通过整章盲还原比较、四层审计并以状态事务完成增量、快照、验收记录、物理章映射和运行台账提交，可作为下一章的直接连续性输入。
- `PUBLISHED`：已对外发布。仍可修改，但修改前必须检查所有依赖它的后续 `VALID/PUBLISHED` 正文；必要时标记受影响章节为待重审。

### 写作包与状态历史

- 冻结场景包记录 commit、直接资料版本/哈希、运行时协议、状态快照、前章、场景地图/滚动计划或 `N/A`、fixture 及文风/前文版本；章节组装包另记录有序场景 DRAFT 哈希、章计划、上一 VALID 章、近期重复窗口和组装协议。任一直接依赖变化后对应包自动 `STALE`，不得继续生成或组装。
- 最新正文运行状态只是当前投影；每章从 `DRAFT` 提交为 `VALID` 时，以 `PREPARED → COMMITTED` 事务同时完成不可覆盖的状态增量、快照、验收记录、物理章映射和运行台账，全部成功后才完成 `VALID` 标记。增量记录前后状态版本、实际变化、悬念、关系/认知、重要物品和已知后续依赖。
- 每3—5章或逻辑事件结束形成 checkpoint，用于验证增量重放后的最新投影。
- 修改旧章时比较新旧增量，沿真实依赖标记后续章节待重审、冻结包 `STALE`，从最早受影响点重放；不依赖该变化的正文无需机械全部降级。

正文质量规则的修改默认不使小说基础模型或全书架构变脏；只有当风格反馈实际上改变作品承诺、人物本质或事件因果时才向上传播。
