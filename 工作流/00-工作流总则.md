> **仓库级公共工作流。** 每次运行先读[项目路由](../项目路由.md)或用户指定的 `项目/<项目名>/`，令 `PROJECT_ROOT` 指向该目录。本目录规则通用于所有小说；作品设定、状态、设计记录、测试运行均存在各自的 `PROJECT_ROOT` 中。

# 小说创作工作流总则

## 1. 工作流目标

本工作流把创作分为“设计”和“编译维护”两类活动：

- Web 对话模型与作者持续问答，按阶段覆盖表把应当讨论的范围问全，并留下完整对话；
- 项目 Agent 逐段读取完整问答，抽取决定、审计覆盖情况、编译项目文件，并维护状态、来源和变更传播。

长对话是产生决定和保存直接证据的过程，不是正式事实库；Chat 在阶段末生成的压缩总结也不具有更高权威。正式项目文件同样不是永远正确；当上游改变时，它们会被标为待重编译。

## 2. 只有三个设计阶段

### 阶段一：小说基础模型

一次连续设计覆盖：作品定位、题材组合、核心卖点、世界基础与世界观、超凡或能力体系、核心机制、主角、核心女主或主要角色、核心人物关系、重要前史、故事基本矛盾、必要结局约束，以及其他足以决定全书方向的基础条件。

完成标准：世界规则、核心人物、能力机制和故事基本前提形成逻辑闭环，足以开始设计整本小说的发展；不要求把所有设定细节提前定义完，也不要求确定每卷剧情。

### 阶段二：全书架构

一次连续设计覆盖：开篇状态、最终状态、全书主要事件链、核心矛盾发展、主角与核心人物发展线、人物关系发展、特殊机制发展、长期伏笔、时间推进、阶段划分、分卷边界、每卷核心任务、卷间因果与结局落点。

完成标准：能说明全书为何从开局走到结局、各阶段承担什么功能、每卷为何存在，但不要求拆成具体章节。

### 阶段三：单卷设计

一次连续设计覆盖：本卷核心目标、主要事件、关键支线、日常内容、人物推进、感情推进、特殊机制或冲突推进、信息揭示、伏笔埋设与回收、本卷节奏、卷首状态、卷末状态及与前后卷衔接。

完成标准：项目 Agent 能据此自动展开成完整逻辑事件链和场景执行方案，不再默认增加一轮“细纲问答”或“正文执行问答”。

## 3. 阶段不是单向锁死

三个阶段代表当前设计问题的尺度，不代表只能向下推进。后续发现问题时可以反向修改：

- 单卷设计可暴露全书架构的节奏或因果问题；
- 全书架构可暴露基础模型的能力、人物动机或结局约束问题；
- 任何反向修改都必须说明保留的设计目标、被替换的实现和实际影响范围。

具体机制见 [`02-项目编译与变更传播.md`](02-项目编译与变更传播.md)。

## 4. 每个阶段内部使用同一套三层问答

三层问答不是三个新的创作阶段，也不是三份独立记录。阶段覆盖表负责“哪些方面不能漏”，三层算法负责“以什么顺序讨论”：

1. 方向与结构：确认本阶段的总体形态和关键设计目标；
2. 关键分叉与缺口：逐域补齐不能可靠推导或后置的必要内容，并处理会显著改变结果的选择；
3. 冲突、后果与覆盖审计：检查逻辑、代价、连锁影响，同时确认阶段覆盖表没有无意识空缺。

详细算法见 [`01-三层问答与设计记录.md`](01-三层问答与设计记录.md)。

## 5. 最短工作路径

### 新项目

1. 把 [`05-交付模板.md`](05-交付模板.md) 中的对话启动模板交给 Web 对话模型；
2. 完成一个阶段的连续问答；
3. 将 Web Chat 的完整连续输出保存到 `PROJECT_ROOT/设计记录/`，不要求 Chat 另写阶段总结；若导出包含双方发言可以一并保留，但当前流程不以此为前提；
4. 让项目 Agent 完整读取、审计，生成编译证据包与本轮当前有效记录；
5. 项目 Agent 只以当前有效记录为正式资料的直接问答来源，再完成编译、链接和变更传播；证据包只负责追溯；
6. 查看 `项目状态.md`、覆盖缺口和编译摘要，再进入下一阶段。

### 已有项目或中途重编

1. 项目 Agent 先建立或刷新 `PROJECT_ROOT/项目状态.md`；
2. 将现有材料分为 `VALID / DIRTY / UNBUILT / BLOCKED / REFERENCE / DEPRECATED`；
3. 选择最上游的 `DIRTY`、`UNBUILT` 或解除阻塞后的节点作为重编起点；
4. 从作者指定的 `REFERENCE` 材料中提取继承候选，先排除必须重做和与新版冲突的内容；
5. 对稳定、低风险候选请求一次批量授权，不逐条重复确认；
6. Web 对话按该阶段覆盖表处理真正需要重新决定的部分；已确认、已授权继承、可可靠推导或明确后置的项目不重复询问，但不能未经检查就跳过；
7. 项目 Agent把获准继承内容编译进新版正式资料，并只传播实际受影响的变化。

### 旧资料批量继承

批量继承是阶段开始前的减负步骤，不是第四个设计阶段，也不会恢复参考库的正式权威。

1. 作者指定可检查的旧资料范围；GitHub 项目模式下可以使用 `项目状态.md` 已登记的参考库范围。
2. Web Chat 或项目 Agent 将候选分为：**明显仍需重新设计、与新版冲突、高概率可以直接继承、低影响可暂时继承**。
3. 前两类不进入批量继承；后两类按主题汇总，让作者进行一次范围授权，例如“除下列项目外，其余未与新版决定冲突的旧人物基础信息继续继承”。
4. 姓名、基础家庭关系、稳定背景、普通生活习惯等低风险信息可以批量处理。
5. 核心世界规则、核心人物本质、作品核心承诺和结局约束等 `HARD` 内容，必须获得当前明确授权或具有当前有效资料支持的明确兼容依据，不能仅因旧版存在而继承。
6. 获准范围必须在完整问答中留下作者授权原文或明确回显，来源类型标为 `INHERITED`，再由项目 Agent 编译到正式资料；正式文件不能直接把参考库当作当前事实引用。
7. 新版决定永远优先。继承项一旦与新版冲突立即失效，不要求新版迁就旧资料。

## 6. 什么时候必须问，什么时候可以推导

必须问作者：

- 两个选项都会改变作品核心承诺、结局、人物本质或世界底层规则；
- 现有确认互相冲突，且优先级和时间顺序无法解决；
- 继续编译会把模型建议误写成作者决定；
- 取舍会造成 `L3` 或 `L4` 影响，而作者未表达方向。

可以直接推导：

- 只有一种实现能同时满足全部已确认约束；
- 是命名、归档、链接、格式或依赖更新；
- 是已确认原因的必要后果，并可清楚把来源类型标为 `DERIVED`；
- 不改变创作方向的局部补缝。

## 7. 项目中的信息层级

从高到低：

1. 用户当前明确指令；
2. 当前对话中作者明确确认的事项；
3. 最新且适用的当前有效记录中的作者决定、继承授权与可靠推导；
4. 当前 `VALID` 的正式项目文件；
5. 由当前有效事实可靠推出的内容；
6. 对应证据包与原始记录中的历史证据；它们用于解决身份、覆盖与遗漏争议，不直接越过当前有效记录获得现行权限；
7. 未经当前授权的参考库、历史大纲和旧正文；
8. Agent 的推断与建议。

较低层不能覆盖较高层。时间较新不等于自动有效：一段新文本若只是模型建议，仍不能覆盖作者旧确认。若证据包或原始记录证明当前有效记录编译错误，应重新编译有效记录与正式资料，而不是在下游临时绕过它们。

## 8. 四层资料与最小文件原则

四层是资料职责，不是四个创作阶段，也不增加作者操作：

1. **原始记录**：作者保存的 Web Chat 连续输出。当前常见格式没有作者发言；每条输出的前半段回显上一轮作者决定，后半段提出下一轮问题。原始记录保留全部时序、选项、建议、重复和覆盖证据，永不改写。
2. **证据包**：项目 Agent 生成的编译证据，保存逐轮处理区原文、旧格式被选方案恢复、原始定位、覆盖/身份争议和迁移比对。它证明有效记录如何生成，但不是当前小说知识库。
3. **当前有效记录**：一个阶段当前仍有效的完整设计语义集合。按主题组织，保留事实、条件、例外、限制、心理、关系、知情、具体事件、因果、设计目标、读者体验、拒绝、后置、最终覆盖和正式映射；不保存逐轮全文、旧筛选稿或大段失效历史。
4. **正式资料**：为下游设计和写作提供可执行接口。有效记录中的每项当前有效、执行相关信息必须在正式资料中获得落点、后置、建议、覆盖或不适用结论，但不逐字复制整份有效记录。

### 原始记录的证据边界

- 模型明确写成“你已确认/你选择/按你的修改/你否定”的内容，可以作为作者决定回显，来源为 `DIRECT`；只有 Chat 输出时，它是可用但非独立复核的间接载体。
- 当决定回显明确指向上一轮的 `A/B/C`、组合项或“按推荐项”时，Agent 必须回到上一轮读取被选方案的完整正文，并与下一轮回显做语义并集；回显中的简写不能替代被选择方案里的条件、例外、形成史、具体实现和叙事目的。自定义修改优先覆盖所选方案中的冲突部分，其余兼容语义继续保留。
- 模型对决定的解释、因果展开和必要后果，需要判断为可靠 `DERIVED`、仅供参考的说明或未获接受的建议；不能因为作者随后回答了新问题，就自动升级为作者决定。
- 下一轮问题中的选项、推荐理由和示例答案只是候选，不属于当前设计事实。明确拒绝项需要保留语义，防止旧方案回流。

### 旧记录兼容与新版原生模式

- **旧记录兼容模式**用于作者回答缺失、确认回显可能只写题号字母或存在旧式总结的记录。Agent 必须回查被选项全文并把恢复材料写入证据包，再编译有效记录。
- **新版原生模式**用于每轮已经明确分为“本轮作者确认 / 模型解释与必要推导 / 下一轮问题”，且确认区完整展开选择语义的记录。默认不再生成被选方案恢复层；只有回显缩略、身份争议或遗漏怀疑时才回查上一轮选项并写入证据包。

### 有效记录的最低完整度

- 简单事实可以是一个信息单元；复杂机制、人物或事件必须拆成足以保留条件、边界和因果的多个部分。
- 必须保留：所有当前有效的独立事实、条件、例外、限制、反例、因果、心理、关系、信息差、具体事件实现、叙事目的、读者体验约束、否定项和事实身份。
- 有效记录可删除无信息增量的重复、已被后文覆盖的大段旧版本、未选择候选、逐轮原文和迁移材料；必要覆盖结论仍留在覆盖清单，完整历史证据留在证据包与原始记录。
- 长记录按主题分节并建立目录；仅在有助于追踪时使用稳定编号，不要求把项目做成逐句数据库。

### 执行相关信息

`HARD / SOFT` 只表示修改成本，不决定是否需要进入正式资料。如果删除一项当前有效信息会改变下游剧情设计、人物表现、知情状态、事件实现、现实条件或正文体验，它就是执行相关信息，必须拥有正式落点。`VALID` 要求不存在未处理的当前有效、执行相关信息。

### 按需读取顺序

1. 当前任务直接相关的 `VALID` 正式资料及其必要正式上游；
2. 正式资料不足以支撑具体执行时，读取当前有效记录中的对应主题；
3. 怀疑遗漏、身份不清、覆盖冲突或重新编译时，读取对应证据包；
4. 证据包仍不足，或必须恢复原始上下文时，回查原始记录。

禁止正文 Agent 默认一次性加载全部有效记录、证据包或原始记录。复杂事件和关键规则应从正式资料链接到有效记录的可定位章节；若发生争议，再从有效记录链接证据包。同一事实只在一个正式负责文件中完整定义，其他文件只在重要依赖处链接。

## 9. 当前项目的特殊状态

当前小说项目的实际阶段与可用状态以 `PROJECT_ROOT/项目状态.md` 为准。进入任何下一阶段前，必须确认上一阶段正式资料为 `VALID`，且其当前编译批次已经存在有效记录。

## 10. 新建小说项目：使用共享项目模板

不要复制工作流。仓库根目录保持 `工作流/` 与 `项目模板/` 两套公共系统，各本小说位于 `项目/<书名>/`。新立项先复制[完整项目模板](../项目模板/00-使用说明.md)，建议运行 `python tools/new_novel_project.py --name 书名 --slug 目录名`；自动建立每书独立的正式资料、设计记录、测试运行和状态，初始阶段一UNBUILT、后续BLOCKED。

新书读取 `PROJECT_ROOT/项目状态.md`，根据适用阶段使用三层问答、证据编译、正式资料编译及传播；未经审计不得将模板占位字段升级为VALID。已有小说则先按[变更传播](02-项目编译与变更传播.md)定位上游最早的DIRTY/UNBUILT阶段。

## 11. 正文是滚动编译产物，不是一次性生成物

三个设计阶段保持不变；正文初始化、章节规划、写作和审计属于执行流程，不构成第四设计阶段。

当某卷单卷设计达到 VALID 后，正文默认采用滚动生产：

正式连续正文先经“文风基线/声音模型/PDM → 卷级场景地图 → 未来3—5章滚动计划 → 当前章基础状态”；完整正文环境测试由“一组连续正式事件 + 测试专用章计划”进入编译，允许卷级场景地图与连续生产滚动计划为 `N/A`，但不得省略章界、章节发动机、场景顺序和整章离开状态。旧中性自由校准、声音资格夹具及 T01—T08 单事件/短场景测试只保留为历史诊断资料，不再是当前正文入口或前置门。

正式连续正文与独立回归汇合为：

场景编译器 → 生成许可 → `FROZEN` 场景单元 → 密封初稿生成器 → `RAW_DRAFT` → B2 有事实边界的小说叙事结构编辑器 → `SCENE_DRAFT` → 章节组装包 → 独立章节组装器 → `CHAPTER_DRAFT` → 整章独立盲还原 → 比较与四层审计/返修 → 状态提交事务 → `VALID`。

- 第一次批量正文前必须使用正式逻辑事件完成至少一次完整物理章正文环境测试并获得作者认可。测试最终稿正文硬下限为 5000 个汉字，必须来自自然的章节范围和叙事密度；自然内容不足时扩大或重编章界，禁止用重复检查、无功能环境、解释性心理或结尾总结凑字。测试使用正常正式资料、冻结场景包、独立 B/B2、独立章节组装、整章独立读者盲读和事实验收；不得用项目外中性样例或单事件短篇建立“声音资格”替代正式剧情中的实际表现。人物声音进入人物执行画像；没有获认可的完整章测试时，不得批量外推正文。
- 物理章是连载叙事单位，不再等到全卷逻辑稿写完后才机械切分；章界先在3—5章滚动计划中提出，场景实际生成后允许版本化调整。多场景正文必须经过独立整章组装和统一验收，不能把若干场景稿直接拼接成章。
- 每个场景生成前必须把正式资料编译为场景事实、人物认知、即时目标、空间/物体、动作因果和对白前提；许可未通过不得冻结。写作包记录直接依赖版本，任一依赖变化自动 `STALE`。
- 初稿生成器只读冻结包、包内本场叙事决策卡、声音胶囊、文风必要片段和必要前文；B2 只读同一包与本次 RAW_DRAFT，在锁定事实/认知因果内重构叙事详略、结构和收束。两者都不读取完整工作流、完整资料、成熟作品分析或回归 oracle。验收器先只读最终 DRAFT 冻结盲还原，再读取写作包比较；回归和高风险章节要求独立上下文。
- 每章通过后先追加状态增量，再更新最新状态快照；每3—5章形成 checkpoint。旧章修改沿增量依赖定位受影响章节和写作包，不靠单个最新快照猜历史。
- 每3—5章进行一次滚动审计，每个逻辑事件结束时进行事件审计，全卷完成后再做卷级总审计。
- 正文状态至少区分 DRAFT / VALID / PUBLISHED。已经发布的章节形成更强连续性约束，修改时必须检查后续已发布内容。
