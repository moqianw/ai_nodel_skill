## 1. 对话布局与隔离边界

| 聊天 | 所在位置 | 唯一职责 | 可读 | 禁读 |
|---|---|---|---|---|
| C 主控 | 项目对话，连接 GitHub | 读取协议、编译新 fixture/冻结包、封包、登记/哈希、归档与调度 | 当前仓库 + 用户传回的本轮产物 | 不把旧失败正文/审查原句混入密封输入 |

| B2 整编 | **项目外**另一全新对话 | 写 `DRAFT` | 同候选三件输入 + 其 `RAW_DRAFT` | GitHub、其他候选、旧评语、Oracle |
| R 读者 | **项目外**另一全新对话 | 无背景纯读者审阅 | 最终正文 `READER_TEXT`（正式章可加上一章可见末尾） | RAW、FROZEN、CARD、声音胶囊、其他审查/历史 |
| F 事实 | **项目外**另一全新对话 | 第一轮盲还原；第二轮对照冻结包 | 第一消息只有最终 `READER_TEXT`；锁定盲还原**之后**再收 `FROZEN` | RAW、其他候选、文学反馈；VQ 无 Oracle |

每**一份**候选都新建 B、B2、R、F 四个独立聊天。C 可持续使用一个聊天。不要把 B2 当成 B 的第二轮消息；R 与 F 不能在同一聊天内充当两个独立审查。R/F 不访问 GitHub，也不要把 `@GitHub` 注入项目外聊天。

使用项目外的普通新聊天；如果平台自动携入项目 AGENTS、历史失败原文或仓库上下文，这个受影响的上下文计 `ISOLATION_INVALID`，重建。避免将旧对话「继续使用」或「复制对话」冒充全新上下文。对话链接/任务 ID 由作者从界面复制交给 C；如无法证明隔离，记 `UNVERIFIED`，**不可假称 `VERIFIED`**。

## 8. 哪些情况需要停止与重开？

- B/B2 意外看过 GitHub、AGENTS、其他候选或旧失败正文：该上下文 `ISOLATION_INVALID`，另开新对话；不算文学 FAIL。
- F 在第一轮盲还原前看过 FROZEN 或 Oracle：该 F 上下文 `INVALID`，另开 F；已读无法撤销。
- 只收到一条 `LITERARY_PASS`、无具体文本判断：`REVIEW_INSUFFICIENT`，补做**新的**独立审查，不把虚假 PASS 算数。
- 事实或读者任一结果 FAIL：不宣布合格，不把其原文评语送回新的 B。C 只归档、诊断负责层；需要修工作流时先更新协议和失效传播，再重跑新封包。
- R 的 `READER_REVISE` 不自动等于 `READER_PASS`；可按当前有效的同候选返修上限处理，但返修稿须新开 R/F 审查，旧审查不能改判。
- H01 未通过：不换掉样本挑一篇碰巧通过的冒充保留测试。诊断后升级协议需重新冻结新的独立样本组。
- 对话 ID 不可得或 GitHub 提交未核实：分别写 `UNVERIFIED` / `WRITE_BLOCKED`，不得自称严格隔离已核验或文件已保存。
- 两类各两篇测试并作者认可后，C 才记录相应 `VOICE_QUALIFIED`；随后严格回归 T05、第一卷连续两章与五到十章才依次开始。手动多对话本身不意味着自动生产已实现。

## 9. 快捷操作顺序

1. C 项目内连接 GitHub，发送第 2 节提示词；取得并核对实际归档的新封包。
2. 新开 B（项目外），复制**C 产出的完整 B 输入**；将 RAW 全文回传 C，C 写 GH。
3. 新开 B2（项目外），复制 C 产出的完整 B2 输入；将 DRAFT 全文回传 C，C 写 GH。
4. 新开 R 和 F（项目外），分别按第 5、6 节先只喂干净终稿；F 第二轮才给 FROZEN。
5. 将 R、F 双轮完整结果发 C；C 核对哈希、编辑损益、审查证据、提交 GitHub，并向作者展示结果。
6. 按预先冻结的另一类别/保留样本继续；最后让作者决定资格。每换候选重复步骤 2—5，并使用全新 B/B2/R/F 对话。

**用户只需复制消息，不手动编辑 GitHub 文件；所有入库均由 C 实际提交并返回 SHA。**
