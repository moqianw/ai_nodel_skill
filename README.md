# AI 小说创作工作流

> **一套通用工作流，多个独立小说项目。** 从作品定位、世界观与人物设定，到全书架构、单卷设计、正文生成、独立审查、状态提交和出版物料管理，统一由工作流组织；每本小说的数据和结果分别保存，不互相污染。

本仓库不是单本小说的大纲仓库，也不是“给一句提示词就能全自动写完小说”的程序。它提供**可追溯的 AI 辅助长篇创作流程、文件结构、初始化模板和检查门槛**。创作决定由作者作出，AI 可以辅助提问、编译与写作；生成后的文学质量仍需独立审查和作者判断。

**快速入口：** [从零开始](#二从零开始创建一部小说) · [目录结构](#一仓库结构) · [三阶段设计](#三从设定到全书与单卷设计) · [样本文风提炼](#1-从参考小说读取和提炼文风) · [正文生产](#四进入正文生产) · [工作流索引](#六公共工作流索引) · [常见问题](#八常见问题)

**文件职责要分清：**

| 位置 | 存什么 | 不应该存什么 |
| --- | --- | --- |
| `工作流/` | 所有小说共用的问答、编译、写作、审查协议 | 某本书独有的人物和情节 |
| `项目模板/` | 可复制的空结构、待填写字段与交付检查 | 已确认的故事事实、已通过的测试 |

任何任务先确定 **`PROJECT_ROOT`**：用户明确指定 `项目/<名称>` 时，以指定项目为准；未指定时读取[项目路由.md](项目路由.md)。目前默认指向 `项目/梦行`。工作流不会自动把其他书的资料读入当前书。

## 二、从零开始创建一部小说

### 0. 准备环境

使用 Git 克隆或下载本仓库。若需要通过命令行创建项目，应安装 **Python 3**；项目初始化脚本只使用 Python 标准库，不要求额外安装 Python 包。创作问答与正文生成需要你能够使用的 AI 对话或 Agent 环境；**Python 脚本本身不调用模型，也不会自动完成小说**。

```bash
git clone https://github.com/moqianw/ai_nodel_01.git
cd ai_nodel_01
```

如果直接在 GitHub 上编辑，也可以手工复制[项目模板](项目模板/00-使用说明.md)，不必运行 Python。

### 1. 初始化新小说项目

在仓库根目录运行：

```bash
# 创建新书，并将其设为默认活跃项目
python tools/new_novel_project.py --name "我的新小说" --slug "novel-01" --activate
```

生成路径为 `项目/novel-01/`，显示书名是“我的新小说”。`--slug` 可省略，省略时目录名默认使用 `--name`；路径不要使用斜杠或与已有项目重名。

常用命令：

```bash
# 只创建，不切换默认项目
python tools/new_novel_project.py --name "第二本书" --slug "novel-02"

# 检查按模板新建的项目，是否缺少模板文件
python tools/new_novel_project.py --name "我的新小说" --slug "novel-01" --check
```

Windows 如未配置 `python` 命令，可尝试 `py -3`。脚本**不会覆盖已存在的项目**；`--check` 仅核对模板文件是否齐备，不代表内容质量合格。模板升级前建立的项目或自定义删减过文件的项目，可能需要单独对照，不能直接把结构不一致视作小说错误。

`--activate` 会修改[项目路由.md](项目路由.md)中的 `PROJECT_ROOT` 行；任务里明确指定其他项目时仍以明确指定为准。切换后可检查路由文件中的人工导航链接是否也需要更新。

### 2. 初始化后先看四个文件

以 `PROJECT_ROOT = 项目/novel-01` 为例：

1. `项目/novel-01/项目说明.md`：填写立项背景、暂定书名和想要创作的基本方向。
2. `项目/novel-01/AGENTS.md`：添加**本书专属**硬约束；不能在这里篡改跨作品公共工作流。
3. `项目/novel-01/项目状态.md`：确认基础模型 `UNBUILT`，后续阶段 `BLOCKED`。
4. `项目/novel-01/正式资料/00-总索引.md`：了解各阶段文件负责什么。

**不要**先把模板文件全部交给 AI 自动补满，更不要把标题、占位示例或模型建议当成作者已确认的设定。第一步是启动**阶段一问答**。

### 3. 启动第一轮作者问答（可复制提示词）

在可读取 GitHub 仓库的 AI 对话中发送：

```text
@GitHub
阅读 main 最新的 AGENTS.md、项目路由.md，
以及 工作流/00、01、05 与 项目/novel-01/项目状态.md、
正式资料/00-总索引.md。

本轮项目固定为：项目/novel-01。
请按照现行工作流，从零开始阶段一「小说基础模型」的连续问答。

先问作品方向与关键结构，再覆盖世界、人物、关系、核心机制、
长期主线与必要终局约束，最后做冲突与覆盖审计。
不要重复已确认的回答，不要把你的推荐方案算作作者决定。
每轮区分「本轮作者确认 / 模型解释与必要推导 / 下一轮问题」。
阶段结束时提示保存完整对话，以便项目 Agent 编译。
```

`@GitHub` 是示例中的 GitHub 连接入口：**只有当前对话环境确实支持并已连接 GitHub 时才能直接读取仓库**。不支持时，按[交付模板的手工粘贴模式](工作流/05-交付模板.md)提供规则、项目状态和有效上游文件。

**问答并不等于写入 GitHub。** 完成一阶段后，需要保存完整对话记录，并让有仓库写入权限的项目 Agent 或你自己编译、提交文件。

### 4. 保存问答，编译阶段成果

建议分工：

- **作者 + 对话模型**：逐轮决定；包括采用、修改、拒绝、例外、后置，不要求作者手动制作复杂的决策表。
- **项目 Agent**：读取完整问答，区分 `DIRECT / DERIVED / INHERITED` 等来源，建立编译证据包与当前有效记录；将结果编入该书的 `正式资料/`；检查冲突及语义遗漏。
- **作者**：核对关键设定与编译结果，决定是否接受以及是否继续下一阶段。

将连续问答保存在 `PROJECT_ROOT/设计记录/`，可使用其中的原始记录模板；保留完整时序，**不要只保存阶段末的 AI 总结**。再将以下请求交给项目 Agent：

```text
针对 项目/novel-01，按 工作流/02-项目编译与变更传播.md
编译刚完成的阶段一原始问答。

生成独立证据包和当前有效设计记录；
将所有有效、执行相关的信息映射到正式资料/01-小说基础模型/；
保留否定、覆盖、条件和明确后置项，不替作者确定未决问题。
执行来源身份、冲突、语义覆盖与跨文件一致性审计。
只有满足VALID条件，才更新项目状态并报告下一阶段。
```

项目 Agent 能否直接写入 GitHub，取决于它是否有相应工具与仓库权限；不能访问时由你自行上传生成的文件。**未经编译审计，不能因为已有 Markdown 文件就宣布 `VALID`。**

## 三、从设定到全书与单卷设计

三个设计阶段只有下面三层；**原始记录、证据包和正式资料是信息层，不是额外创作阶段**。

| 设计阶段 | 需要确定什么 | 文件位置 | 何时能继续 |
| --- | --- | --- | --- |
| **阶段一：小说基础模型** | 作品定位、世界、能力/特殊前提、人物与家庭、关系、前史、长期边界、必要终局 | `正式资料/01-小说基础模型/` | 形成逻辑闭环、有效记录和审计，状态 `VALID` |
| **阶段二：全书架构** | 开篇到结局的主因果、人物与关系长期发展、阶段分卷、每卷功能、伏笔、现实时间线 | `正式资料/02-全书架构/` | 能解释为何从开局走到结局、卷与卷怎样相接，状态 `VALID` |
| **阶段三：单卷设计** | 本卷卷首/卷末、事件链、人物选择、日常支线、关系变化、知情及现实连续性 | `正式资料/03-单卷设计/第XX卷/` | 事件足够可执行，完成卷级编译审计，当前卷 `VALID` |

阶段二启动示例：

```text
@GitHub
当前项目：项目/novel-01。
读取工作流/00、01、05，以及本项目VALID基础模型和项目状态。
开始阶段二「全书架构」的连续问答，完整覆盖主因果、
人物关系发展、时间跨度、阶段分卷、卷间依赖和结局，
不要提前展开成逐章正文。
```

阶段三以**某一卷**为单位。首次进行时将[卷模板](项目模板/正式资料/03-单卷设计/卷模板/00-使用说明.md)复制到本书 `正式资料/03-单卷设计/第01卷/`，再建立该卷问答、证据与有效设计资料；后续卷依次进行。

如果单卷设计发现原设定不合理，可以反向修改全书架构或基础模型，但要同步更新依赖状态，不能悄悄覆盖旧事实。详见[项目编译与变更传播](工作流/02-项目编译与变更传播.md)。

## 四、进入正文生产

**当前流程不允许从一句“写第一章”跳过上游资料和独立质量测试直接批量生成。** 对应卷有效后，才按以下顺序运行：

### 1. 从参考小说读取和提炼文风

**这一步是正文初始化的一部分，不能只让 AI 按默认风格直接写第一章。** 公共[正文语言与长篇稳定性协议](工作流/06-正文语言与长篇稳定性.md)已经规定：从作者认可的正文和明确授权的成熟作品中提炼叙事方法，再形成**本书自己的文风基线、正文声音模型和 PDM**。它不新增第四个设计阶段，也不等于模仿某位作者的文字。

1. **指定参考样本与目标。** 先问作者使用哪些参考作品、分别借鉴什么体验。当前仓库[参考库/样本/](参考库/00-使用说明.md)中已有[《轮回乐园》样本](参考库/样本/轮回乐园.txt)和[《龙族》合集样本](参考库/样本/龙族（1-4合集）.txt)；**存在不等于自动授权新书使用**。可增添作者有权使用的其他片段，也可以只使用作者明确认可的本书正文。明确不适合当前题材的部分。
2. **按功能而不是随机页数取样。** 从获授权的样本中选不同位置和功能的代表片段，例如开篇进入、普通日常、熟人对话、心理与情绪变化、动作/冲突、场景过渡和章节收束。样本小说可能很长，**按需分段读取，不必也不应把整本书装进模型上下文**。记下来源文件、取样范围和功能，但生成器不接收原文。
3. **分析“怎么写”而非“写了什么”。** 观察叙事距离、段落重心与换段时机、心理出现/停止的条件、对白怎样嵌入行动、主语及感知承载者连续性、场景详略与省略、转场和章末落点、轻重节奏与读者获得感。对每类提取**触发 → 保留 → 省略 → 停止 → 转向**的决策，以及不该照搬的反例；可用结构统计寻找异常，但不把句长/对白比例设为死指标。
4. **跨作品归纳、适配本书。** 比较多处样本，提炼可以迁移的叙事功能，排除特定作品的角色、世界、独创设定、剧情、标志性措辞和高度可辨认表达；再结合**本书作者要求、人物模型与题材**进行取舍。某种方法即使在参考作品有效，也不表示必须用于本书。
5. **把分析转成可执行文件。** 在 `PROJECT_ROOT/正式资料/04-正文/` 使用[样本文风提炼模板](项目模板/正式资料/04-正文/05-样本文风提炼与迁移.md)记录样本覆盖、观察、拒绝项、可迁移规则及来源；将稳定特征编入本书的 `01-文风与读者体验基线.md`，把场景功能路由、短声音胶囊和**叙事决策模型（PDM）**编入 `02-声音模型与叙事决策接口.md`。若引用本书自己的已认可正文，也标明版本。它们还必须经过正式章测试，**单纯分析完成不等于声音资格通过**。
6. **用新书真实剧情验证。** 编译器只把当前场景需要的决策卡、声音胶囊、文风摘要和必要前文放入 `FROZEN` 包；独立 B/B2/CA、读者 R、事实 F 和作者在[完整章环境测试](工作流/07-正文冷启动与回归测试.md)中验证实际读感。反馈差异先修负责层，再用新包复测；不要把失败例句和测试答案喂回初稿生成器。

**可直接交给分析/编译 Agent 的提示词：**

```text
当前项目：@Github
请先读取工作流/06-正文语言与长篇稳定性.md、
本项目的VALID人物与题材约束以及参考库的使用边界。

本次只分析我明确授权的参考样本：[填写样本文件或章节范围]。
按场景功能抽取有代表性的片段，分析叙事距离、心理、
对白与动作衔接、段落主语、详略、转场及章节收束。
说明哪些写法可迁移、哪些是来源作品的专属表达而应排除。
不要复制原文，不要模仿特定作者的识别性文字。

请先生成本书的样本文风提炼记录，再编译文风基线、
正文声音模型、PDM、场景决策卡和短声音胶囊。
这些是待验证的本书模型，不登记VOICE_QUALIFIED或正文PASS；
后续只用本书VALID卷级事件做完整章环境测试。
```

**重要边界：** 参考作品原文、可识别句式和取样分析**不进入正文生成器输入**。此分析环节由可访问授权样本的分析/编译侧完成；正常正文生成器只读裁剪后的抽象写作约束和故事事实。若作者不使用外部参考，应明确记下“无授权外部样本”，以作者要求和本书认可正文为依据，不能虚构读过样本。

### 2. 为本书建立正文执行资料

在 `PROJECT_ROOT/正式资料/04-正文/` 建立/校准该书专属的文风基线、声音模型、人物执行画像、叙事决策模型（PDM）和连续性状态。**先完成上述授权样本的分析/适配（如果有），再编译和校准这些文件**。其他书的文风资格或已通过结果不能自动移植。

### 3. 首次进行完整章环境测试

使用该书 **VALID 单卷设计里的连续正式事件**，先建立测试专用章计划，再执行独立的正文生产与验收链：

```text
连续正式逻辑事件
  → 测试专用完整章计划
  → 场景事实/认知/动机/空间编译与许可
  → FROZEN 密封场景包
  → 独立 B 生成 RAW_DRAFT
  → 独立 B2 整编 SCENE_DRAFT
  → 独立 CA 组装唯一 CHAPTER_DRAFT
  → 独立 R（整章读者盲读）＋独立 F（事实盲还原/对照）
  → 作者判断与测试归档
```

- **测试章硬要求：正文至少 5000 个汉字**，且必须有自然的章内内容；素材不够就调整章界/连续事件范围，不能注水。这是**完整章环境测试**的门槛，**不是所有正式连载章节的最低字数**。
- 生成 B、整编 B2、组装 CA、读者 R、事实 F 需要**真正隔离的上下文**；同一个聊天窗口让模型轮流扮演五个角色，不算有效独立审查。
- R 检查阅读趣味、人物表现、段落与叙事体验；F 先独立还原正文事实，再对照冻结包检查一致性。事实通过不等于文学质量通过。
- 双门通过仍需要**作者实际认可**。未通过的稿件留在 `PROJECT_ROOT/测试运行/<run_id>/` 作为历史证据，不能把旧失败答案/Oracle 反馈灌给下一轮生成器，也不能直接登记为正式正文。

对应规范：[完整章环境测试](工作流/07-正文冷启动与回归测试.md) · [运行时协议](工作流/08-正文运行时协议.md) · [读者体验和假阳性防护](工作流/10-读者体验与假阳性防护.md)。

### 4. 正式逐章生产

通过适用完整章测试且作者同意后，按[章节组装与连续生产](工作流/09-完整章节组装与连续生产.md)执行：

```text
VALID 单卷设计
  → 卷级场景地图
  → 未来 3—5 章滚动计划
  → 当前章计划 + 最新状态
  → 顺序生成、整编场景
  → 独立章节组装
  → 整章读者/事实审查与返修
  → 追加章节状态增量 + 更新状态快照
  → 提交章节状态 VALID
  → 刷新下一轮计划
```

正文**逻辑事件 ≠ 场景 ≠ 物理章**。一个逻辑事件可以跨多章，一章也可以包含多个场景。日常连载章可以按约 2500 字作为初步规划信号，章界和实际篇幅服从叙事需要；不可把多份场景稿未经整章组装就直接拼接成 `VALID`。

每 3—5 章形成滚动检查点；失败时按状态增量与依赖重新处理，不在上一章仍不确定时盲目续写。区分 `DRAFT`（候选）、`VALID`（正式验收）和 `PUBLISHED`（已发布、受更强连续性约束）。

## 五、如何管理项目与 GitHub

### 作品切换与多人协作

- 切换默认项目：`python tools/new_novel_project.py --name "书名" --slug "目录" --activate` **只用于创建新项目时一并切换**；已有项目请直接编辑[项目路由](项目路由.md)的 `PROJECT_ROOT`，或在对话中明确指定 `项目/<名称>`，**不要重复执行创建命令**。
- 多对话协作：控制/编译对话可以看到必要的正式资料；B、B2、CA、R、F 分别只接收各自允许的输入。跨对话传递要通过实际封包、文本和文件引用，不是口头声称隔离。历史手册可参见[11-人工多对话隔离测试与GitHub归档](工作流/11-人工多对话隔离测试与GitHub归档.md)，其中退役的旧 VQ 测试**不能复活为新书前置门**。
- Agent 更新资料后应提交至仓库，并说明实际修改、依据、依赖和失效传播；多人同时编辑时先检查最新 `main`，避免覆盖其他人的提交。


脚本不会自动 `git commit` 或 `git push`。如果在另一台设备上编辑了仓库，先同步最新提交（例如 `git pull`），再开始新一轮工作。

### 状态速查

| 状态 | 意义 | 下一步 |
| --- | --- | --- |
| `UNBUILT` | 这个阶段尚未建成 | 按有效上游开始设计 |
| `BLOCKED` | 必要上游尚未满足 | 先完成上游，不越级 |
| `VALID` | 当前版本通过对应编译/验收 | 可以供下游使用 |
| `DIRTY` | 已有资料受上游更改影响 | 按影响范围重编 |
| `STALE` | 冻结包、测试或生成输入依赖的版本已变化 | 重新编译输入，不能沿用旧包 |
| `REFERENCE` | 历史资料或参考样本 | 仅在授权且兼容时继承 |
| `DEPRECATED` | 旧入口或旧协议已退役 | 不能当当前执行依据 |

**`VALID` 是有边界的状态**：基础模型 `VALID` 不意味着全书、单卷或正文已经完成；上一部小说的 `PASS` 也不等于新小说的 `PASS`。

## 七、常见问题

**Q：能直接让 AI “从零写第一章”吗？**  
可以让 AI 写试验性文本，但那不等于经过当前工作流的正式正文。正式生产至少需要当前卷 `VALID`、对应声音和叙事决策资料、适用完整章环境测试以及章节状态管理。

**Q：项目初始化后为什么全是 `UNBUILT/BLOCKED`？**  
这是正确的。模板创建的是文件骨架，不是自动生成的世界观或已获作者认可的故事。按阶段完成记录、编译、审计后才更新状态。

**Q：完整章测试为什么要求 5000 汉字？正式章节也必须 5000 吗？**  
不是。5000 是完整章**环境测试**的最低覆盖要求；正式连载章节按照当前故事的自然章界和篇幅计划执行。

**Q：只用一个对话窗口可以完成独立 R/F 验收吗？**  
不能把同一上下文中的角色扮演当作独立审查。应使用真正隔离的上下文，并留存输入版本及证据；不具备条件时可做非正式自查，但不能登记为已通过独立双门。

**Q：旧书、已发表作品或参考样本能否直接用？**  
[参考库](参考库/00-使用说明.md)默认为 `REFERENCE`。旧书事实需要作者明确授权、核查兼容并正式编译；文学样本须作者明确选择并授权分析，按功能取样后提炼成**本书自己的叙事决策和声音模型**。不能把参考小说全文、原句、专有设定或识别性表述发给正文生成器。详见[从样本提炼文风](#1-从参考小说读取和提炼文风)。

**Q：如何换一本小说而不影响工作流？**  
新建 `项目/<新书>/`，在[项目路由](项目路由.md)改变默认项目，或每次操作明确指定项目路径。`工作流/` 只维护一份；每本书独立保存 `AGENTS.md`、`项目状态.md`、`正式资料/`、`设计记录/`、`测试运行/` 和 `出版物料/`。

**Q：某个阶段被改了，是否要全部重做？**  
不一定。按[变更传播协议](工作流/02-项目编译与变更传播.md)确认最上游修改、受影响下游与过期封包；只重编实际依赖被改信息的部分，历史记录保留而不重新标作当前事实。

---

**建议首次使用的最短路线：** 创建新项目 → 读 `AGENTS.md` 与路由 → 阶段一连续问答 → 保存原始记录 → Agent 编译并审计 `VALID` → 阶段二 → 第一卷阶段三 → **选择授权样本、提炼叙事方法并编译本书文风/声音/PDM** → 完整章测试与作者认可 → 正式滚动逐章写作。
